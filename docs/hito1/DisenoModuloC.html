c) Respuestas razonadas

1. ¿Por qué se consulta estabaAutorizado y no estaAutorizado?

Decisión: se pregunta si el emisor estaba autorizado en la fecha de emisión. Razón: con el presente, todos los títulos de un funcionario dejarían de ser válidos el día que cambia de cargo. Alternativa descartada: estaAutorizado, que invalida títulos legítimos ya emitidos.

2. ¿Por qué el estado se comprueba antes que el compromiso?

Decisión: orden Inexistente → EmisorNoAutorizado → Revocado → Suspendido → DocumentoAlterado → Valido. Razón: la situación de un título no depende del documento presentado; un título revocado con un documento distinto debe dar «Revocado», no «documento alterado». Alternativa descartada: comprobar el compromiso primero, que da un veredicto engañoso.

3. ¿Por qué verificar es view?

Decisión: no modifica estado. Razón: no cuesta gas a quien consulta ni exige billetera, que es el objetivo del proyecto. Alternativa descartada: emitir un evento con el veredicto, lo que exigiría una transacción firmada y pagada.

4. ¿Por qué byteAceptado solo acepta bytes menores que 252?

Decisión: se descartan los bytes 252 a 255. Razón: 256 = 7 × 36 + 4; con byte % 36 los símbolos 0 a 3 recibirían 8 bytes y los otros 32 solo 7 (14 % más probables). Con 0 a 251, cada símbolo recibe exactamente 7 bytes. Alternativa descartada: b % 36 directo (sesgo de módulo).

5. ¿Por qué el contrato no genera el azar?

Decisión: derivarLocalizador recibe una semilla de 32 bytes y la transforma de forma determinista. Razón: todo lo que ocurre en la cadena es público y reproducible, así que un contrato no tiene azar seguro; la semilla la genera el emisor fuera de la cadena con un generador criptográfico. Alternativa descartada: block.timestamp o blockhash, predecibles o influenciables.
